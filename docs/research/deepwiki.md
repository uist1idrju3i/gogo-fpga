# DeepWikiの構成と検査

この文書はWikiを保守する開発者向けです。[調査の索引](../../RESEARCH.md#7-分割した調査)から参照できます。設定の正本は [`.devin/wiki.json`](../../.devin/wiki.json) です。Wikiは派生した案内であり、実装、テスト、原記録の代わりではありません。

## 公式仕様と採用した範囲

2026-11-27に[DeepWiki repository wikisの公式説明](https://docs.devin.ai/work-with-devin/deepwiki)を再確認しました。設定には `repo_notes` と、空でない `pages` が必要です。設定がある場合は自動のページ選定を置き換え、列挙したページだけを生成する仕様です。足りない主題が自動で補われることを前提にしません。

[Validation Limits](https://docs.devin.ai/work-with-devin/deepwiki#validation-limits)には次の上限があります。

| 項目 | 公式説明 | 本リポジトリーの検査 |
| --- | --- | --- |
| ページ数 | Maximum 30 pages (80 for enterprise) | 通常枠の1から30ページ。リポジトリーの設定は30ページちょうど |
| ノート総数 | Maximum 100 total notes | repo_notesと全page_notesの合計100件まで。リポジトリーの設定は100件ちょうど |
| ノート本文 | Maximum 10,000 characters per note | 各contentを10,000文字まで |
| タイトル | Page titles must be unique and non-empty | 重複・空白だけのタイトルを拒否 |

`repo_notes` の要素は必須の `content` と任意の `author` を持ちます。ページには必須の `title`・`purpose` と任意の `parent`・`page_notes` を使います。`page_notes` は `content` を持つノート配列として検査します。親の省略と `null` を受け付け、ページの順序には依存しません。

確認した公式ページにはWikiの言語を英語に限定する規定や、言語専用の設定項目はありません。AGENTS.mdに従って本文と見出しを日本語にし、その生成指示もrepo_notesへ明記します。識別子やパスは英語のままです。

公式説明には生成のeffort levelとしてlow、medium、highがあり、mediumとhighはACUを使います。この変更はリポジトリーの設定ファイルを更新するもので、再生成やeffort levelの変更は行いません。

## 30ページ構成へ更新した理由

更新前の設定は20ページ・27ノートでした。一方、2026-11-27時点の公開中のDeepWiki構成には、設定ファイルにない10ページが表示されていました。追加されていた主題は、ブラウザー要件、教師役・採点、端末内補完、外部ソースへのpatch、ビルド高速化、文書の自動検査、Surfer組込み、solver通信、SBY・Python実行基盤、反例再実行の監査です。

この差があると、次の再生成で重要なページが消える可能性があります。そこで公開中の主題を設定に取り込み、30タイトルを登録しました。

## 初めて使う人の読み順へ変更した理由

2026-11-27に[公開Wikiの概要](https://deepwiki.com/uist1idrju3i/gogo-fpga)を確認しました。先頭の子項目はアーキテクチャーで、公開サイトを開いてサンプルを試す手順が本文にありませんでした。また、配信先をGitHub Pagesと記載していました。本リポジトリーでは[Cloudflare Pages](pages-delivery.md)を使い、[fpga.moe](https://fpga.moe/)の応答でCOOP/COEPヘッダーを確認できました。

タイトルと扱う主題は維持し、概要を開いた人に公開サイトとLチカの始め方を先に示します。読み順は「Web IDEとプロジェクト管理」「対応ボードと制約」「ブラウザー内の構成とデータの流れ」「ビルドとCIの検査」「開発参加とエージェントの規則」です。

- Web IDEはブラウザー要件から始め、プロジェクトの保存・ZIP、VerilogシミュレーションとSurfer、HDLライブラリー、端末内補完、任意のAI相談へ案内します。OpenRouterと教師役の詳細はAI相談から読みます。
- 対応ボードから書き込みの手順と安全性へ案内します。構成とデータの流れは合成・配置配線・ビットストリーム作成を追い、形式検証からsolver・SBY・反例監査へ進みます。
- ビルド・CIは再現性、Cloudflare Pagesでの公開、仮想USB、パッチ、高速化と計測を扱います。開発参加はUX契約、調査記録・Wikiの保守、文書の自動検査を扱います。

親子関係や順序を変えた後の個別ページのURLは、公開Wikiの再生成後に確認します。

## 100ノートの使い方

ノートには、生成時に参照する資料と説明に残す条件を書きます。配分は `repo_notes` 10件と、30ページそれぞれの `page_notes` 3件です。

repo_notesには、製品の範囲、表記、根拠の優先順位、生成物と固定版、工程の境界、書き込み、配信、OpenRouter、AI機能、形式検証に共通する指示を置きます。

page_notesは各ページで次の3種類に揃えます。

1. 根拠とするリポジトリー内のパス。バッククオートで囲み、実装・テスト・調査のうち、当該ページで使うものを挙げる
2. 生成したページで答えること。画面の操作、入出力、構成や検証範囲を具体的に示す
3. 説明に残す条件。失敗の判定、対象外の機能、仮想と実機の違いなどを示す

依存の版や性能値を設定へ転記せず、pin checkerや固定条件付きの実験へ戻る構成です。IDCODE、FAILログによる失敗検出、実機未確認、形式検証のunknownや資材未準備、mockと実サービスの差はrepo_notesと該当ページで保持します。

現在の機能はコードとテスト、設計の背景はRESEARCH.mdと`docs/research/`、測定は`docs/experiments/`、画面契約は`docs/ux/`で確認します。初期計画と後続の実装が食い違うときは、時点と確認できる範囲を付けてください。外部ソースの接続やライセンスを説明するページでは`vendor/`や`third_party/`も参照できます。生成した`public_html/`や`docs/ux/out/`には生成元への参照を添えます。

## 検査と更新

```sh
python3 .github/scripts/check-deepwiki.py
python3 -m unittest discover -s tests/check-deepwiki -v
```

lint workflowで両方を実行します。検査はPython標準ライブラリーだけを使い、公式の通常枠の上限に加え、このリポジトリーの保守方針として次を拒否します。

- 読取り失敗、不正なUTF-8・JSON、重複JSONキー、NaNなどの非標準値
- 必須項目の欠落、型の不一致、未知の項目、空白だけの本文・目的・author
- タイトル前後の空白、存在しない親、自分自身や複数ページを巡る親の循環

文字数はPythonの文字列長で数えます。公式説明に具体的な数え方の記載がないため、この方式をローカル検査の基準とします。30ページ、合計100ノート、10,000文字の境界と、正常・空・不正入力をテストします。このリポジトリーの設定では、30ページ、10件のrepo_notes、各ページ3件のpage_notesを確認します。以前の設定に欠けていた10主題、概要からの読み順、主な利用ページの親、各ページの根拠ノートで参照するパスも検査します。公式に項目が追加されたときは、仕様を確認してから検査とテストを更新します。

## 再生成後の確認

設定がmainに入った後、公開Wikiを開き、新しい構成が反映されているか調べます。更新操作を利用できる場合は[公式の手順](https://docs.devin.ai/work-with-devin/deepwiki#getting-started)に沿って再生成します。

1. 概要の最初にfpga.moeへのリンクとLチカの手順があり、開発ツールのインストールが不要であることと、対応ブラウザーが必要であることが伝わる。
2. ブラウザー要件、4種のTang Nano、書き込み先とIDCODE、仮想USBの検査範囲をたどれる。書き込みの説明に実機の確認状況が記載されている。
3. 配信先がCloudflare Pagesと記され、GitHub Actionsの検査と人間による公開承認が区別されている。
4. Verilogシミュレーション、形式検証の実行条件、OpenRouterへの任意の送信が区別されている。
5. 概要から各ページを開け、説明に付いたソースリンクが根拠の箇所を指している。既存の個別ページURLを共有している場合は、そのリンクも確かめる。

リポジトリーの検査は設定の構造と参照先を対象とします。再生成後の文章とリンクは公開Wikiで確認します。
